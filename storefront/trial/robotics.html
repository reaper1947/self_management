Robotics with ROS 2 · Module 1

Nodes, Topics & the ROS 2 CLI

Every robot in this course is the same shape: small programs that publish and subscribe to named streams. Learn to see that graph from the command line and you can debug any ROS 2 system — including the ones you did not write.

🎉 Lesson complete. You have run a real ROS 2 graph and driven a robot by hand — Module 2 is writing your own nodes in Python.

What you need

~10 min to install · no robot hardware, nothing to buy

  • Ubuntu 22.04 with ROS 2 Humble (LTS), or Ubuntu 24.04 with Jazzy. Every command below works on both.
  • Two terminal windows. That is genuinely it.
  • The demo packages, which ship with the desktop install: demo_nodes_cpp and turtlesim.
sudo apt install ros-humble-desktop ros-humble-turtlesim
source /opt/ros/humble/setup.bash     # every new terminal needs this

Not on Ubuntu?

Run it in Docker on any OS — docker run -it --rm osrf/ros:humble-desktop — or in a virtual machine. The full course sets up a Docker workspace that keeps your host clean.

Step 1 · The compute graph

The one mental model the whole course rests on

ROS 2 is not an operating system and not a language. It is middleware: a common way for many small programs to find each other and exchange typed data, even when they were written by different people, in different languages, running on different machines.

ConceptWhat it is
NodeOne process that does one job — camera_driver, path_planner
TopicA named, typed stream. Nodes publish to it or subscribe to it. Many-to-many, anonymous.
MessageThe typed cargo on a topic — geometry_msgs/Twist, sensor_msgs/Image
ServiceA request/response call — like calling a function on another node
ActionA long-running goal with feedback that you can cancel — "drive to X"

The default is publish/subscribe. A planner publishes a velocity command to /cmd_vel; a motor controller subscribes to /cmd_vel. Neither node knows the other exists, and either can be restarted, replaced, or moved to another computer without touching the other's code. That decoupling is the entire point.

[ teleop ] --/turtle1/cmd_vel (Twist)--> [ turtlesim ] --/turtle1/pose (Pose)--> [ your node ]

Nodes are boxes. Topics are arrows. Messages are the cargo.

Quick check: the motor controller crashes and restarts. What has to change in the planner?

Its connection settings, to point at the new process Nothing — it keeps publishing to the same topic It must re-register with the ROS master

Step 2 · Run two nodes

One command per terminal · source in each one

Terminal 1 — a node that publishes a string once a second:

source /opt/ros/humble/setup.bash
ros2 run demo_nodes_cpp talker

Terminal 2 — a simulated robot you can actually see:

source /opt/ros/humble/setup.bash
ros2 run turtlesim turtlesim_node

A blue window opens with a turtle in it. You are now running a real ROS 2 graph: two independent processes that found each other automatically, with no configuration file and no central server.

"Package not found"

You forgot to source /opt/ros/humble/setup.bash in that terminal. It applies per shell, not per machine. Put it in ~/.bashrc once you are settled on a version.

Step 3 · Look inside the graph

The CLI is your debugger for the rest of the course

Open a third terminal. Everything below is read-only — you are inspecting a live system.

ros2 node list                        # who is running
ros2 node info /turtlesim             # its publishers, subscribers, services, actions

ros2 topic list -t                    # every topic, with its message type
ros2 topic info /turtle1/cmd_vel -v   # publishers, subscribers and QoS
ros2 topic echo /turtle1/pose         # print the messages as they arrive
ros2 topic hz /turtle1/pose           # how fast they are arriving

ros2 interface show geometry_msgs/msg/Twist   # what fields a Twist actually has

Watch the output of ros2 topic echo /turtle1/pose. The turtle broadcasts its position many times a second and nothing is subscribed to it. That is normal — a topic exists whether or not anyone is listening.

The 90% rule

Almost all ROS debugging is two questions answered by two commands: is the data there (ros2 topic echo) and is it fast enough (ros2 topic hz). When Nav2 misbehaves later in the course, it is nearly always one of those two answers coming back wrong.

Step 4 · Publish a message yourself

You are now a node

ros2 interface show geometry_msgs/msg/Twist tells you a Twist carries a linear and an angular vector. The turtle reads linear.x (forward speed) and angular.z (turn rate). So publish one by hand:

ros2 topic pub --rate 1 /turtle1/cmd_vel geometry_msgs/msg/Twist \
  "{linear: {x: 1.0}, angular: {z: 0.8}}"

The turtle drives in a circle. Nothing in turtlesim was written to expect you — it subscribes to a topic, and you published to that topic. A joystick, a path planner and your terminal are interchangeable here, and that is exactly how the rover comes up in the capstone.

Two more, while the graph is live:

ros2 service call /clear std_srvs/srv/Empty     # a request/response call
ros2 param set /turtlesim background_b 255      # change a setting at runtime

The turtle keeps moving after Ctrl-C

It holds the last velocity it was given. Publish a zero Twist to stop it — and note that a real robot behaves the same way. Safe shutdown is a design problem, not an afterthought.

Your challenge

Do this before moving on

  1. Drive the turtle in a square using only ros2 topic pub — straight, stop, turn 90°, repeat.
  2. Run ros2 topic echo /turtle1/pose in another terminal while you do it, and watch theta to check your turns.
  3. Use ros2 topic hz /turtle1/pose to measure the publish rate, then explain why ros2 topic echo alone could not have told you that.
